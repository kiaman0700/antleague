# 기능 설계서 (game-feature-spec)

이 게임은 규칙(엔진)·서버(api)·DB(Supabase)·모바일 화면·PC 화면이 얽혀 있다. 바로 코드를 짜면 "서버는 바뀌었는데 화면이 안 바뀜", "정보가 상대에게 새어 나감", "진행 중인 게임 가격이 바뀜" 같은 문제가 뒤늦게 터진다. 그래서 **코드 전에 설계서 1장**을 쓰고 사용자에게 보여 준다.

## 질문은 최소로

사용자는 빠르게 결정하는 편이다. 모호한 점은 **1~2개만** 묻고, 나머지는 합리적인 기본값으로 채워서 설계서에 "기본값: ~ (바꾸려면 말씀해 주세요)"로 적는다.

## 설계서 항목 (짧게, 표·목록으로)

`design/<기능-이름>.md` 로 저장하고 대화에도 요약한다. 사용자에게 보여 주는 글은 **한국어, 쉬운 말**.

1. **한 줄 요약** — 플레이어 입장에서 무엇이 달라지나
2. **규칙** — 숫자까지 구체적으로 (시간·확률·비용·인원별 차이). 1대1과 3인 이상이 다르면 둘 다
3. **서버가 정하는 것 / 화면에 보내는 것** — 가격·비용·결과는 서버 계산. 화면 데이터(`buildView`/`sliceMarket`)에 새로 들어가는 값과, **절대 들어가면 안 되는 값**(미래 가격, 상대 거래·카드, 진실 여부, 시드 등)을 표로
4. **DB 변경** — 새 테이블·컬럼·제약. 필요하면 `supabase/00N_이름.sql` (여러 번 실행해도 안전하게), 적용 전에도 서버가 죽지 않게 할 방법
5. **진행 중인 게임에 미치는 영향** — 같은 시드의 가격이 바뀌면 안 됨. 새 난수가 필요하면 별도 난수 스트림
6. **화면** — 모바일(세로·가로)과 PC 각각 어디에 무엇이 보이는지. 스크롤바가 새로 생기지 않게
7. **악용 시나리오** — 일부러 안 누르기, 눌렀다 취소하기, 동시 요청, 다른 사람 방 ID로 요청, 값 조작 등과 막는 법
8. **완료 기준 체크리스트** ★ — 관찰 가능한 문장으로. 각 항목은 나중에 `game-self-check` 에서 테스트 하나가 된다
   - 예: "[ ] 1대1에서 한 명이 마감하면 남은 시간이 90초 이하가 된다 (e2e)"
   - 예: "[ ] 감별기를 안 쓰면 화면 데이터에 가짜 여부가 없다 (단위 테스트)"

## 관문: 승인 후에만 코드

설계서를 보여 주고 "이대로 만들까요?"라고 묻는다. 사용자가 고치라고 하면 반영한다. **승인 전에는 게임 코드 0줄.** (설계서 파일·조사용 읽기는 괜찮다)

승인되면 `test-driven-development` 로 엔진 규칙부터 테스트를 쓰고 구현한 뒤, 끝나면 `game-self-check` 로 완료 기준을 전부 확인한다.
